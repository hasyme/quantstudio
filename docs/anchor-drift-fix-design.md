## 0.5 缺陷拆分总览（v3 核心变更）

### 0.5.1 两个缺陷

| 维度 | **缺陷1：minutes raw 污染**（本文档） | **缺陷2：daily front 冻结**（独立立项） |
|---|---|---|
| 落点 | `_restore_to_raw`（adapter 还原层） | `qfq_reanchor_*`（重锚编排层） |
| 污染列 | `close`（raw 被 ×ratio 放大） | `close_front`（未随因子演进重锚） |
| 时间线 | 2026-08 起（P1-③ 之后） | 2025-03 起（重锚上线前存量）+ 2026-08 后因 raw 污染被阻断 |
| 触发源 | MCP 分钟路径 | MCP 日线路径 × 重锚编排（发现但未生效） |
| 根因状态 | **已证实**（9/9 逐位吻合） | **已定位方向**（`rows_stock_daily=0`），实施前需补代码路径取证 |
| 影响面 | stock_minutes 13,309 单元格 + etf_minutes 1,327 单元格 | stock_daily.close_front 430 只、54,442 行 |

### 0.5.2 拆分决策（用户裁定 2026-09-27）

**代码修复拆成两条流水线**，理由（实锤）：
1. 两个缺陷**不同根、不同子系统、不同时间线**（见上表）；
2. 合并 = 把根因未证实的缺陷2 塞进根因已证实的缺陷1 方案 → **带病实施**，违反「根因未证实不得修」；
3. 合并使「纯增益、不修一送一」**无法分别验收**（哪个缺陷被哪个改动证明零回归）。

**但缺陷1 必须先行**（因果耦合，非完全独立）：

```
缺陷1 raw 污染 → 重锚引擎 daily_raw_mismatch/minute_raw_mismatch → 阻断/回滚 → 缺陷2 无法修复
```

> 证据：MCP reanchor_event 中 290 条 blocked（`daily_raw_mismatch` 248 条）+ 585 条 rolled_back
> （postcheck「分钟 front 不匹配」）—— 全是缺陷1 raw 污染的直接次生。缺陷1 修好后，重锚引擎
> 不再被 raw_mismatch 阻断，缺陷2 的重锚才能落地。

### 0.5.3 数据修复合并规划（关键补充）

代码修复拆分，**数据修复合并规划**：重拉受影响 `(code,day)` 这一动作**一次同时修好两列**——
`close` 靠还原修正后的代码、`close_front` 靠 aligner 用当前因子重算。故数据层不拆成两遍重拉，
代码层才拆成两条流水线。缺陷1 的验收须覆盖数据层的两列同修，但缺陷2 的「存量重锚」仍属其自身流水线。

### 0.5.4 对方案 A 参考真值的降级

P1-4 全量验证发现 `stock_daily` **并非 100% 自洽**（front 列 430 只污染）。但污染的是 `close_front`，
**不是方案 A 所依赖的 `close`（raw 列）**。故方案 A 参考真值从「默认可信」降级为「验收时显式验证 raw 干净」
（见 §5.2 新增项），而非推翻方案 A。

## 1. 问题定义

### 1.1 现象

`[QualityAudit] AdjustmentAnchorDrift` 报 `stock_minutes` **1099 只** code 偏离（max dev 1.0988），
每次运行错误集完全相同，成为管线门禁的**固定阻断项**。

### 1.2 根因（已证实）

**唯一错误源头**：`MCPAdapter._restore_to_raw`（`mcp_adapter.py:1835`，入口 `_restore_qfq_if_required:1617`）
对价格列**无条件**施加还原公式：

```python
ratio = adj_latest_local / adj_i          # line 1958
out[col] = out[col] * ratio               # line 1959-1960，price_cols = OHLC + pre_close
```

该公式**仅在「云端值为前复权」时成立**。取证证实云端复权状态**按日期异质**：

| 云端返回 | 特征 | 证据 |
|---|---|---|
| **raw**（不复权） | 值 == 本地日线 raw | 100/107 = 93.5%；如 000012 @ 06-15 云端 4.11 = 日线 4.11 |
| **qfq**（前复权） | 值 × ratio ≈ 日线 raw | **7/107 = 6.5%**；如 000012 @ 07-15 云端 3.859，×1.005362=3.8797≈日线 3.880 |
| `is_qfq` 标志 | **恒 True，不可信** | 抽样 31,812 行全部 `is_qfq=True`，与上述两种状态均不符 |

**已证实的充分失效条件（不依赖 front 下游形态）**：

> 当云端返回 **raw** 而 `_restore_to_raw` 施加 `×ratio` 时，
> 落库 `close = raw × ratio`（被放大）。**000012 偏离行 9/9 逐位吻合**（4.1100×1.005362=4.1320→4.13）。

**关于 `close_front` 列——诚实声明（对应 P0-1）**：早期版本曾先后给出「front 不受影响」与
「front=raw 全错」两种互相矛盾的确定性表述，两者均**过度简化**。实测显示 front 列存在**多条写入路径、
多种最终形态**（全量 13,309 单元格中「front 正确」45.3%、「两列互换」28.8%、「raw 存了 front」8.1% 等），
本方案**不声称已逐一归因**这些形态。**关键在于：方案 A 只修源头（raw 列）**，修复后 aligner 会从
正确 raw 重新推导 `front = raw × adj_i/adj_latest`（`aligner.py:985-988`，该契约已被日线 100% 验证），
**所有下游形态一并复位，无需逐一归因**。

### 1.3 关键代码事实

- `mcp_adapter.py:1842-1850` 注释载明 **P1-③（2026-08-03，commit `f7df29c`）**决策：
  > 「**全部行走还原公式，不按 is_qfq 分流**……is_qfq=False 行并非真 raw，而是旧基准前复权」
  该决策基于**单点观测**（300182.SZ 108x），**未考虑云端状态的日期异质性**（本取证已证实）。
- `_RESTORE_MISSING_FACTOR_FAIL_FAST = True`（`mcp_adapter.py:298`）：只守「因子**缺失**」；
  「因子存在却被**误施加**」这条路径无任何守卫——即本次缺陷。
- aligner native 白名单 `{"baostock","akshare","xtquant"}` **不含 `mcp`**（`aligner.py:414`），
  故 MCP 必走 `_apply_qfq` 计算 front。

### 1.4 P0-4 归因：7/107 偏离行

那 7 行（H1「云端 close == 日线 raw」不成立）**全部是 `000012`，日期 2026-07-10 ~ 07-21**：

```
云端 close = 3.7100（小），日线 raw = 3.7300（大），diff≈0.02（0.53%）
cand_qfq = 云端 × ratio = 3.7299 ≈ 日线 raw ✓
```

**结论**：这 7 行云端返回的是 **qfq**（非舍入差），且落库 `close` 因还原公式而对 qfq 输入**工作正常**
（`落库 close == 日线 raw`，drift=0）。这证明两点：

1. **还原公式本身无错**——错的是它对 **raw 输入也照施不误**；
2. **云端状态是 (code, 日期) 异质的**——同一只 000012，6 月 raw、7 月中下旬 qfq。→ 方案 A 必须
   **per-(code, day)** 判定，不能按批次单点判定（否则「某批某日 qfq」会被当 raw 跳过还原而漏放大，
   或相反）。

### 1.5 次生问题：审计漏检

`AdjustmentAnchorDrift` 只验「两列**互**不自洽」（`quality_audit.py:694-696`）。两列同向偏移时静默通过。
漏检最严重者：**600649 @ 2026-06-25，落库 close=57.13 vs 真值 3.50（+1532%），审计 drift=0 未告警**。

### 1.6 影响面

**缺陷1 范围（本文档）**：
- `stock_minutes` 不复权列在 **13,309 个 `(code,day)` 单元格**失真，偏差 0.3% ~ **+1532%**。
- **>5%：158 只；>20%：112 只；>50%：16 只。**
- 受影响日期带：2026-03-02 ~ 2026-09-04（109 个交易日）。
- `etf_minutes`：**12 只 code、1,327 单元格**（P1-6 已实测，形态偏「两列互换/raw 存 front」，量级轻于 stock，无 >100% 极端值）。
  **对账说明（审计第三轮 P2-3）**：审计告警 53 只 → 实测失真 12 只，差异与 stock 同源——
  审计 A1 口径含 front-only 错误与过报，实测按「close_front/close 偏离 adj_i/adj_latest」严格判定得 12 只。
- **任何直读分钟不复权价的策略/回测在受影响区间得到错误价格。**

**缺陷2 范围（独立立项，不在本文档）**：
- `stock_daily.close_front`：**430 只 code、54,442 行**（除权后历史 front 未重锚）。

## 3. 候选方案

### 方案 A —— 数据驱动 per-(code,day) 状态判定（**推荐·主**）

在 `_restore_to_raw` 内，**不以 `is_qfq` 为准**，按 **(code, 交易日)** 用本地日线 raw 反推云端实际状态：

```
对每个 (code, day) 的收盘参考 bar（分钟表取 14:59~15:01 最后一 bar；日线表即当日行）：
    ratio    = adj_latest / adj_i
    ├─ |ratio − 1| ≤ ε → **直写短路**：raw == qfq 数学等价，无需判定、无需参考（覆盖新日期，见 §3.1）
    ├─ ratio ≠ 1：
    │    raw_ref  = 本地 stock_daily.close（不复权真值）；etf_minutes 用 etf_daily.close（R5）
    │    cand_raw = cloud_close                          # 假设云端已是 raw
    │    cand_qfq = cloud_close × ratio                  # 假设云端是 qfq
    │    ├─ 无参考（本地日线该日无行）→ **不写** + 告警 + 下批重试（选项 A，见 §3.1）
    │    ├─ 仅 |cand_raw − raw_ref| ≤ tol → 判 raw  → ratio 不还原
    │    ├─ 仅 |cand_qfq − raw_ref| ≤ tol → 判 qfq  → 照旧还原 ×ratio
    │    ├─ 两者均命中         → 判 raw（无副作用路径，见 P0-3）
    │    └─ 两者均不命中       → **fail-fast**（不写库）
```

- **tol（P0-3）**：**绝对 0.01 元 且 相对 0.1%** 双门槛都满足才判命中。
  （依据 P0-4 归因：qfq 行的真实偏离 ≈0.53%，raw 行的 diff=0；0.01 元/0.1% 可清晰区分且不误伤日内舍入。）
- **双命中裁决（P0-3）**：`ratio≈1` 时 `cand_raw≈cand_qfq`，还原与不还原数学近似等价——判 raw、不还原
  （无副作用路径）。
- **双不命中 fail-fast 通道（P0-3）**：`logger.error` + `batch_audit.status=failed` + 抛 `ValueError`
  （复用 `_RESTORE_MISSING_FACTOR_FAIL_FAST` 语义），**不静默写库**。
- **正面论据（对应审计 P0-2）**：日线未被污染而分钟被污染，说明云端行为**按 freq 异质**——数据驱动判定
  天然兼容此点，这是 A 优于「按 is_qfq 分流」或「按表硬编码」的核心理由。
- **写入顺序耦合（R1 已裁定 2026-09-27）**：判定依赖本地日线已就位。
  - **分钟表**：靠「先日线后分钟」的批次顺序保证日线先落库，消除「无参考」路径（已定案）；
  - **日线表自身**：**裁定 = 选项 A（不写 + 告警 + 下批重试），并叠加「ratio≈1 直写捷径」**——详见 §3.1。
  - 无论哪种，**禁止静默直通或静默照旧还原**（两者均有污染风险）。
- **挂接点（P1-3）**：判定器须挂在**流式两遍流程第二遍**（`cand_qfq` 依赖 adj_latest 快照，只有第二遍才
  有全量注入后的全局最新因子）。

### 3.1 日线表「无参考」裁定（2026-09-27，最终决定）

**裁定：选项 A（无参考 → 不写入 + 告警 + 下批重试），叠加「ratio≈1 直写捷径」作为成立前提。**

> 关键事实：`ratio = adj_latest / adj_i`。当 `|ratio−1| ≤ ε` 时 `raw == qfq`（数学等价），
> 还原是无操作、判定无意义。对某 code 的**最新交易日**，其因子即全局最新因子（该日之后无除权），
> `adj_i == adj_latest → ratio == 1` 恒成立。**故日线增量新日期天然无需参考、无需判定，直接写入，零延迟。**
> 取证佐证：本次污染全部落在历史重拉日期带（2026-03-02 ~ 09-04），从未出现在新鲜交易日——正是 ratio=1 的体现。

「无参考」仅在 `ratio≠1` 且本地无同日 close 的**历史缺日**出现（该缺日本身即数据质量异常）：

| 场景 | 处理 | 延迟 |
|---|---|---|
| 新日期（ratio≈1，raw==qfq） | 直接写入，不判定 | 无 |
| 历史日期（ratio≠1，本地有 close） | 正常判定 | 无 |
| 历史缺日（ratio≠1，本地无 close） | **不写入 + 告警 + 下批重试**（选项 A） | 该日延迟一/数批，待补全日线后重试 |

**否决选项 B**：维持 always-restore 等于把日线完整性押在一个**未验证的云端假设**上——与本次缺陷
（`is_qfq=True` 恒真却与值不符）同构；若该假设失效，日线将以「close 放大 + front=raw」的同向偏移
静默污染，且现有审计（只验两列互自洽）会像 600649 一样漏检，代价是又一轮全量对账取证。

**实施细节（选项 A 落地要求）**：
- 无参考告警须带 `(code, date, 原因=历史缺日)` 字段，并计入可观测计数（防静默累积）；
- 重试设上限（建议 3 批），超限升级为「需人工补全日线」告警，避免无限静默重试；
- `ε` 取浮点容差（建议 `1e-6`，或直接复用双命中 tol 判「ratio≈1」）。

### 方案 B —— 写库前校验门（**建议与 A 并施**）

写库前抽样校验：**同时**验 `close` 对 `stock_daily.close`、且 `close_front == close × adj_i/adj_latest`
（覆盖 aligner 侧回归，P2 建议），不一致即 fail-fast。

- **定位**：作为 A 的**兜底防线**，不单独采用（不修复存量、抽样有漏网风险）。

### 方案 C —— 云端契约修复（**外部依赖，并行上报**）

要求 MCP server 使 `is_qfq` 真实（或恒返 raw / 恒返 qfq 并给可信标志）。

- **定位**：并行上报，**不作为本方案实施前提**（否则缺陷无法本地闭环）。

### 方案 D —— 关闭还原开关（`enable_qfq_restore=False`）

- **否决（维持原判）**：若云端恢复返回 qfq，直通会造成双重复权（300750 实测）；「换错误不换根」。

### 推荐组合

> **方案 A（主）+ 方案 B（兜底）+ 方案 C（并行上报云端）**；否决 D。

## 4. 数据修复（与代码修复同等必要）

代码修复**只防新增**，**不修复存量**。须配套数据修复：

1. **两列同修（数据修复合并规划）**：受影响单元格的 `close`（可能被放大）与 `close_front`（可能=raw）
   一并复位；重拉在修复后代码下执行，aligner 从正确 raw 重新推导 front，两列**一次重拉一起复位**。
2. **受影响边界（P1-2 规则化 + R6 升级）**：候选集从「除权日 ∈ [now-120d, now+7d]」**扩大为**
   `ex_date ≥ 2026-03-02`（最早受影响日期）的全部 code——因污染机理是「8/9 月批次重拉 3 月旧行 ×
   ratio≠1」，除权日落在 120 天窗口外的 code 同样受害。漏检追查从个案式（600649）改为**窗口规则式**：
   对候选集内所有 code，全量比对 `stock_minutes.close` 对日线 raw（不依赖审计告警）。
