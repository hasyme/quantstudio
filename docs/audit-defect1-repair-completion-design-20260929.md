## 2. 发现（按严重度排序）

### F1（P0，阻断）根因 B「失败后无退避重放」与日志事实不符——5 小时空转的真身是另一条链

**日志复验结论（决定性）：**

- 2026-09-28 daemon.log 全天仅 **2 条 ERROR**；唯一的 `export_exceeds_time_budget` 在 **12:21:58**（streaming batch 126 失败那一次）。
- 13:18–18:16 所谓「空转」窗口内 **0 条 ERROR**。不存在「同一处再次失败」的循环。
- 「export 分批=128」共出现 **115 次**，逐条比对上下文可知**每次对应不同 code**：这是 `qfq_resident_orchestrator` 的**逐股重锚链**（13:14 起先 ETF 逐只、13:18 起个股；`ReanchorCheck` 000002→000534 共 47 只通过，约 6.4 分钟/只），每只 code 做一次全窗（128 个 2 天网格批）的逐批 export_cache 命中拉取。
- 该窗口内 `stock_minutes` **writer 写入 0 次**（全日志 0 条 `[DuckDBWriter] stock_minutes` 写入行）。

**真实机理**：任务失败后，`execute_task` 的 finally 分支在 `task_ok=False` 时**仍执行** `qfq_run_post_ingest`
（`daemon.py:662-666`：仅 `_cancelled` 才跳过）→ QFQ 常驻编排器进入事件发现 / fresh capture / 逐股重锚链
（日志：12:37 `qfq_event_discovery`，13:14 起逐只 capture）→ 5,247 只 × ~6.4 min/只 ≈ **数周量级**。
这就是「5 小时 CPU ~120%、零写入」的真身：**不是重试循环，是失败任务后无界执行的 QFQ 收尾链**。

**对方案的影响**：
- P2 的改动点（「daemon 源链失败分支」加确定性错误不重放 + 重试上限）与真实现象**错位**——源链对每个源只执行一次，
  真正的空转发生在 execute_task 之后的 QFQ post-ingest 链，P2 碰不到它。
- mcp client 层**已于 2026-09-18（六步③）具备**完整重试纪律：`retry_max=5` + 退避 `(30,60,120,240,480)s` +
  总预算 `retry_budget_sec` + 确定性/瞬时错误分类不重试（`mcp/client.py:155-167`、`416-427`、`533-597`）。
  P2 拟做的「确定性错误不重放」在 client 层已存在，属重复建设。
- 验收 B1（构造 budget 错误验证重放收敛）将**空转通过**——它验证的是一个不存在于生产事故中的循环。

### F2（P0，阻断）P1 软停止机制不覆盖实际失败相位——两次事故都死在 fetch 阶段，而软停止只能在写阶段触发

**代码事实**：
- `_streaming_export` 的调用序是：`_resolve_shard_paths`（`mcp_adapter.py:1596-1626`）**先循环创建全部 136 个
  export 作业并逐批落盘，全部完成后才返回分片迭代器**；daemon 的逐片 align→validate→write 在此之后才开始。
- 软停止的唯一触发点 `_task_boundary` 只在**每片写完**后调用（`daemon.py:1322-1326`）→
  **fetch 阶段（~4.4 min/批 × 136 批 ≈ 10 小时）没有任何边界可停**。

**日志复验（run 2 决定性证据）**：daemon.log 末尾，run 2（export_async=true）从 20:00 前后逐批推进，
终止于 **22:20:18「export 批次 28/136」**——看门狗杀死的是 fetch 阶段的批循环，彼时**一片都未 yield、一行都未写**。
run 1 的 budget 错误（batch 126/136）同样发生在 fetch 阶段。

**推论**：
- `--max-runtime-min 100` 在 fetch 阶段**永远不会触发**；两次历史失败恰恰都在该相位，P1 机制对它们完全无效。
- 游标只在写片后推进 → fetch 期间游标不动 → 下一轮 `_open_day_resume` 命不中 → fetch 窗口无法缩小。
  §7.3「100 分钟/轮 × 约 7 轮」的时间预算**不成立**（每轮 fetch 都要覆盖整个剩余窗口）。
- **A1 小样本验收会假阳性通过**：3 批小窗的 fetch 秒级完成，写片边界随即触发软停止，恰好绕开被审计的相位。
  A1 通过 ≠ 前提成立。方案 ⚠ 注把这个前提列为「跨进程游标跳过已写数据」，**问错了问题**——真正未验证的前提是
  「fetch 阶段可被软停止中断」。

**附带修正（证据链内部矛盾，须一并裁决）**：
- 方案 §1.2 根因 A 表述「流式写入语义为『全部分片成功后才推进水位/提交』→ 整体不落库」**后半句错误**。
  代码事实：每片 write 独立连接、无显式事务、upsert 后关连接（`writers.py:788-860`）→ **逐片即持久**；
  「全部片写完后一次」的只有**水位**（`daemon.py:1343-1350`）。
- 「两次重跑零写入」的真正机理 = **fetch 前置全量完成之前不产生任何分片**（F2），而非写事务回滚。
  诊断纠正文档 §1 的判断（autocommit 逐片持久）是对的，根因确证文档 §5.4/§6.1 的因果解释（「整体不落库」）
  是错的；方案同时引用了两说，未裁决。

### F3（P1）软停止在 once CLI 路径的出口未定义

`execute_task` 捕获 `TaskCancelled` 后 re-raise（`daemon.py:661`）；`run_once`（`daemon.py:2192-2201`）无捕获
→ 软停止将以未处理异常终止 CLI（栈跟踪 + 非零码）。实施必撞。方案应定义 once CLI 层的收口语义
（明确「软停止收口、进度已持久化」的日志文案与退出码，与硬失败区分）。

### F4（P1）「MCPExportBudgetError = 确定性错误」的分类依据不足，且与 A3 存在依赖矛盾

- attempt1 §4.1 自认 budget 边界未取证（疑服务端**当日累计负载/配额**）。若属「随时间恢复」类，
  归入「确定性、不重试」会误杀次日可成功的重跑；若属「请求规模」类，则批次 126–136 可能**永远过不去**，
  A3（≥99.5% 一致率）不可达——而方案把缩窗（`minute_export_target_rows`）划为「另案不阻塞」。
  **若 budget 错误属第二类，「另案」就不再是可选优化而是 A3 的前置依赖**，方案须给出判定实验。
- B1 用「超小 row_limit 触发 budget 错误」构造确定性失败——与生产触发条件（服务端预算）成因不同，验证效力有限。

### F5（中）A3 的残留行风险未讨论

upsert 修复**不删除本地多余行**。若存在「本地有、云端无」的污染行（如根因确证 §4 的 784 组仅有 14:59
占位 bar 的 code-day），重拉无法清除。A3 判据按 (code, day) 配对计算可能不受影响，但残留脏 bar 对策略层
仍是风险。建议 A3 验收增加「重拉前后行数差 / 多余行清单」核查步骤，或显式声明该残留与后续清理另案。

### F6（低）文字瑕疵

§1.3/§1.4「判废**三重**校验」实际列了四项（schema_version / task+mode / 窗口指纹 / 水位）。

## 3. 返工建议（方向性，不要求推倒重写）

1. **重写根因 B**（对应 F1）：定性改为「once 路径任务失败后 `qfq_run_post_ingest` 无界执行逐股重锚链」。
   P2 改为对该链加界——失败任务跳过 post-ingest，或为其加运行预算/可中断边界；client 层既有重试纪律
   （retry_max/退避/预算/确定性分类）保留不动，仅在方案中引用确认。P2 改动点从「daemon 源链失败分支」
   移到 execute_task finally / qfq_run_post_ingest 的进入条件。
2. **P1 增补 fetch 相位可中断性**（对应 F2），二选一或组合：
   - a) 在 `_resolve_shard_paths` 的批循环加边界检查（响应软停止谓词；游标按已 fetch 日期推进——因写入幂等，
     「已 fetch」与「已写」可等价对待，但须在方案中显式论证）；
   - b) 不改流式语义，改用**窗口分段驱动**：每轮 CLI 限定子窗口（start/end），利用既有 export_cache（TTL 7 天）
     天然分轮——这是最小改动路径，与「不新造机制」的初衷最贴合。
3. **A1 验收强化**（对应 F2）：必须包含「fetch 阶段超过软停止预算」的场景（大窗 + 小预算），
   证明软停止能中断 fetch；或明确声明不能、并以 §3.2-b 替代。
4. **A3 增加残留行核查**（对应 F5）。
5. **裁决证据链矛盾**（对应 F2 附带项）：以 writer autocommit 事实修正根因确证文档 §5.4/§6.1 的因果表述
   （update_time 证据保留，「整体不落库」的解释更正为「fetch 前置全量、未产出分片」）。
6. **补充 budget 错误定性实验**（对应 F4）：一次小成本探测（如对 batch 126 同窗口在次日重试一次 create_export_job）
   判定「配额类 vs 规模类」，据此决定缩窗是否升级为前置依赖。
