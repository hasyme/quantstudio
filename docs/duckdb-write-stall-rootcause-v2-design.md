## 0. 结论摘要（审计入口）

1. **R2（DuckDB 1.4.5 组件缺陷）已在生产现场复现**（门6，2026-10-03 01:28:27，第 56 批写完、
   第 57 批永不返回，单核满载、日志/DB 零增长），与 10-02 两次事故**同一边界**（表内约 2.75M 行）。
   三次事件同点 ⇒ 确定性触发。
2. **W1 已把"无限静默挂起"降为"900 秒内确定性收敛"**（S1 600s → interrupt；S2 300s → 诊断落盘 →
   `os._exit(75)`），并**实证 interrupt 对本病态无效** ⇒ S2 必需。
3. **H5' 离线复现全部失败**（4 组，见 §1.3）：即使"生产同序"（约 1180 万行、生产库副本、真实行）
   在离线进程中也**不复现** ⇒ **不存在可离线验证修复效果的复现环境**；任何"根治"措施无法在
   交付前被实证，只能 (a) 以"等价语义 + 失败无害"论证上线，(b) 用**在线受控实验**验收。
4. **主线 = L0-A 停摆自动降级重试**：首次停摆（W1 捕获、事务已回滚、零数据损失）时，自动改用
   **语义等价**的 `DELETE 重叠键 + 纯 INSERT` 重试**同一批**；成功则流水线继续（落降级审计），
   再失败则任务失败。既可能绕过 `ON CONFLICT` 算子，又在失败时**不产生任何数据损害**。
5. **不改写生产语句形态作默认**：停摆在 `ON CONFLICT`（903）与纯 INSERT（915）**两条语句**上都发生过
   （事故2 判定为 915），改写语句不能证明规避 ⇒ 只做"停摆后降级"。

## 3. 改动设计

### 3.1 L0-A 停摆自动降级重试（主线）

**落点**：`writers.py::_write_locked`（捕获 `DuckDBWriteStalled`）+ 新增等价降级写入路径。

机制（零行为变化前提：只有"已停摆"这一异常分支才走）：

    ON CONFLICT / 纯 INSERT 语句
       └─ W1 捕获停摆（事务已由 interrupt 回滚，零数据损失）
            ├─ 开关 QS_DUCKDB_WRITE_STALL_FALLBACK=1（默认开）且本批尚未降级过
            │     → 记 WARNING + 计数
            │     → 用等价路径重试同一批：DELETE (code,time) IN (SELECT ...) + INSERT 纯 INSERT
            │     → 成功：写批照常返回 WriteResult（new/updated 沿用写前计数），日志标注 (stall-fallback)
            │     → 再次停摆/异常：原样抛出，任务失败
            └─ 开关关闭或已降级过：原样抛出（等价 v1 行为）

**等价性论证（DELETE+INSERT 等价于 ON CONFLICT DO UPDATE SET 全列）**

- 目标态：主键命中批内键的行 = 批内对应行（全部列取新值），其余行不变。
- `ON CONFLICT DO UPDATE SET c=EXCLUDED.c ...`（全列）正是"该行被批内行完全替换"。
- `DELETE 命中键 + INSERT 批内行` 得到同一目标态。
- 前提（已由既有测试钉死）：批内主键已去重（`writers.py:790`）、列投影显式一致、
  `WriteResult` 计数取自**写前** `SELECT COUNT`（降级不改变计数口径）。
- **可观察差异（如实标注）**：行物理存储顺序会变（DELETE+INSERT 追加到表尾）。框架内读路径均带
  `ORDER BY`/PIT 条件，不依赖物理顺序；验收须以"带 ORDER BY 的黄金结果逐项一致"为准，
  禁止以无序 `SELECT *` 的行序作为验收依据。

**默认值取舍（提请审计裁定）**：建议**默认开**（C2 失败无害 + 门6 已证该表当前无法完成）；
若审计认为"改变写入物理形态"需更保守，则保留 `QS_DUCKDB_WRITE_STALL_FALLBACK=0` 关闭开关。

### 3.2 L0-B 批内子批化（并行措施，低风险）

大表把单条 5 万行 DML 切成 5k 子批逐条执行（同连接；单事务规模下降）。语义等价、幂等。
- 开关：`QS_DUCKDB_WRITE_CHUNK_ROWS`（默认 0=关；建议在线验证时开 5000）。
- 风险：批间存在"部分提交"窗口（崩溃时前半已提交）；写入幂等，重跑收敛，不产生脏数据。

### 3.3 L0-C 在线受控验收（唯一有效验收）

真实 `mcp_stock_daily` 重跑（`--mode once --pull-mode incremental --config-dir config/profiles/mcp_only`）：
1. 基线（现行 W1，不开 L0-A/B）：已知会在第 57 批停摆（门6 已证，不重复消耗）；
2. 开 `QS_DUCKDB_WRITE_STALL_FALLBACK=1`：观察第 57 批是否经降级重试成功并继续；
3. 若 2 失败，开 `QS_DUCKDB_WRITE_CHUNK_ROWS=5000` 再跑；
4. 通过判据：写批数 **不少于 60**（越过原停摆边界）且日志/DB 持续增长、无未捕获异常；
   若整轮跑完（165 分片）则记录"全量回填完成"。

### 3.4 L0-D 上游报告（并行，非阻塞）

把三次事件 + 门6 复现证据（时间线、诊断 JSONL、native 栈、确定性边界）整理为 DuckDB issue 材料；
R2 维持 `BLOCKED(外部依赖)`，解除条件 = 上游修复或后续版本实测不含缺陷。

### 3.5 明确不做（本轮）

- 不升级 DuckDB（C3：无法离线验证；`duckdb_version_gate` 会拒 1.5.x，牵动 case008 口径）；
- 不改分片维度（按 code 分片会改变 MCP 导出契约与对齐口径，超出稳定性修复范围）；
- 不把 delins 设为默认写入形态（C1）。

## 附：H5' 复盘（本轮最重要的方法论产出）

1. **合成数据复现无效**：四组离线回放（最大 11.8M 行、生产库副本、真实行数据、生产同序）
   全部无法复现停摆 ⇒ "复现"必须使用真实生产链路，**离线等价环境不存在**。
2. **判据纪律仍然有效**：本次判定"是否停摆"依旧用四项同时看（进程存活 / 日志推进 / DB 字节 /
   CPU 与产出耦合）。门6 正是靠"CPU 30s 窗口 29.6s + 日志静止 127s + DB 静止 734s"判定停摆，
   而非靠"进程还在"就下结论。
3. **修复自身也可能挂**：门7 演练曾因替身不响应 interrupt 且关闭 S2 而自身空转 ⇒
   任何注入式验证都必须自带硬截止，且**不得为了跑得快而关掉兜底**。
