## 1. 严重问题（Blocker）：不修正即不得进入实施

### B1 【严重】`passthrough_export_fallback=false` 时是否**跳过首页探测**未定义 → 回退后比修复前更差，M5 未闭环

- **位置**：§3.2 步骤 1（L121-128）、§3.4 表（L154）、§6.1（L225-227）
- **问题**：§3.4 仅写 `false = 首页超时维持旧重试语义`；§6.1 称置 false 即「恢复修复前通道行为」。但按 §3.2 步骤 1 的字面实现，探测 `_fetch_all_pages(..., max_attempts=1)` 是**无条件执行**的，降级才是受开关控制的分支。若开关关闭而探测仍在，则原本靠第 2~5 次重连重试试探成功的表（P3-2 10053/ECONNRESET 场景，`client.py:576-588`）**只尝试 1 次即失败** → 回退状态比修复前**更差**，直接命中 §6.3「原 72 个成功任务出现新失败」的回退判据。
- **修改建议**：在 §3.2 步骤 1 与 §3.4、§6.1 三处统一写死——
  > `passthrough_export_fallback=false` ⇒ `_fetch_all_pages` 传 `max_attempts=None`（**完全不探测**），§3.2 全部三个分支均不生效，`_fetch_passthrough` 与修复前逐行等效。
  - 并在 §5.1 增加一条单测：开关关闭 + 首页超时 → 调用序列与修复前完全一致（5 次尝试）。

### B2 【严重】探针只覆盖 8 表，但降级会把**任意** passthrough 表导入 export 通道 → 未探表的窗口下推无证据，存在 M6 同类的「清空表」风险

- **位置**：§3.0（L73-74，探针对象 = 7 张宽文本表 + `ws_asfund`） vs §3.1.2（L89-92，「探针对**该表**通过时才下推」） vs §3.2 步骤 2（L129-130，降级复用 3.1 全部能力）
- **问题**：§3.2 的降级是**通用**的——任何走 `_fetch_passthrough` 的表首页真超时都会降级到 export。实测走该通道的有 **62 张（库内）/ 50 张（跑批口径）**（见 §2 数字核对），而探针只覆盖 8 张。一旦第 9 张表（例如 `moneyflow_ths`，220 万行）触发降级，就会在**没有任何行数等价证据**的情况下套用窗口下推；passthrough 是 `CREATE OR REPLACE` 全量覆盖语义（`daemon.py:988-991`），下推若不匹配服务端过滤列 → 0 行 = **直接清空目标表**。这等于把 M6 已封堵的风险从 8 张表放大到 62 张表。
- **修改建议**（三选一，写死进 §3.0/§3.1.2）：
  1. **白名单制（推荐）**：新增 `passthrough_export_window_tables: [...]` 显式名单，仅名单内表下推窗口；名单 = 探针通过的表；未列名单一律不下推（仅异步 + 分片）。
  2. 探针覆盖**全部 62 张** passthrough 表（成本可接受，均为只读双跑）。
  3. 降级路径**强制不下推窗口**（降级只做异步 + 分片收缩 + 0 行守卫），窗口下推仅限 7 张宽文本表。
  - 无论选哪种，§3.0 的探针对象描述、§3.1.2 的门控条件、§4.2.1/§4.2.2 的影响面数字必须同步改写。

## 2. 中等问题（Major）

### M-1 数字错误：「69 个 passthrough 任务（fetch_page）」把配置数与通道数混用

- **位置**：§4.2.2（L169）、§4.2.3（L169-172）、§3.2.5（L134-135）、§4.3 表（L181）
- **实测**（`collector_tasks.json`）：库内 88 任务 / 启用 74；passthrough 69（启用 57）；宽文本 7 张（全部启用，走 **export** 通道）；**实际走 fetch_page 的 passthrough = 62（库内）/ 50（跑批）**。
- **问题**：「69」是库内 passthrough 总数，其中 7 张根本不走 fetch_page；且跑批口径只有 57 张 passthrough。v1 的「51 张」同样不准（应为 50）。§3.2.5「首页一次成功的表（当前全部 69 个 passthrough 任务的实际状态）」表述亦不成立。
- **建议**：统一改为「62 张走 fetch_page 的 passthrough 表（跑批口径 50 张）；7 张宽文本走 export 通道」；§4.3 表同步。

### M-2 `client.py:580` 仍按 `self.retry_max` 判定 → 「不空转重试」失真，§4.3/§5.6 数字不可复现

- **位置**：§3.2 步骤 1（L121-128）、§4.3（L181）、§5.6（L218-219）
- **代码事实**：`client.py:580` 为 `if attempt + 1 < self.retry_max:`（**用的是 `self.retry_max`，不是本次调用的有效 attempts 上限**）；`:589-595` 末次才跳过退避。故 `max_attempts=1` 的探针在单次超时后**仍会 sleep `backoff[0]`=30s**（且对传输错误仍会 `_reset_connection`）再抛 `MCPTransportError`。
- **影响**：① §3.2「不空转重试」不成立（实际空转 30s）；② §5.6「构成 = 首页探测 ~90s」应为 **~120s**；③ 重发分支（`max_attempts=retry_max-1`）的实际退避序列取决于实现者是否顺带修 `:580`，两种实现的总退避分别为 210s 与 480s，§4.3「时延微调」不可判定。
- **建议**：在 §3 改动表与 §3.2 中明确——`client.py:580`（及 `:589-595` 末次跳退避判定）必须改用**本次调用的有效 attempts 上限**；并据此把 §5.6 构成改写为「首页探测 ~90s（单次调用上限）+ export 异步等待」，§5.1 增加断言「`max_attempts=1` 路径总 sleep == 0」。

### M-3 §5.3 验收口径内部冲突：`success ≥ 59` 与 `empty 集合逐项一致` 互斥

- **位置**：§5.3（L210-212）
- **问题**：若 F-1/F-2 修复后成功但返回 0 行，台账会记为 `empty`（`daemon.py:1432-1435`），此时 `empty` 集合必然与 20261004 的 15 项不同（而 `failed=0`、`success=59`）——两个判据不能同时成立，验收时无法裁定。
- **建议**：改为——「`failed = 0`；`success ≥ 59`；`empty` 集合 ⊆（20261004 的 15 项 ∪ {`mcp_llm_text_events_enriched_pt`, `mcp_ws_asfund_pt`}）」；若两任务返回 **0 行**，须额外给出「该表在服务端确为 0 行」的证据，否则判为验收不通过。

### M-4 §6.1「恢复修复前通道行为」范围过宽：3.1.3 / 3.1.5 无配置键，回退后仍生效

- **位置**：§6.1（L225-227）、§3.4（L151-155）
- **问题**：三键置 false 只覆盖「降级 / 窗口下推 / 异步」。**§3.1.3 的 `MCPExportBudgetError` 分片收缩**与 **§3.1.5 的 0 行守卫**没有对应配置键，配置回退后依然存在。修复前这两条路径是「异常直接上抛 → 任务失败」，回退后是「捕获并分片重试 → 可能成功」，严格说不等价。
- **建议**：二选一——(a) 为两者各加一个配置键（如 `passthrough_export_shard_retry`），或 (b) 在 §6.1 明确写下：「§3.1.3/§3.1.5 为**纯增益错误路径**逻辑，无回退键；修复前该路径必然失败，故不构成等价性差异」。

### M-5 §3.0「任一表不通过 → 全局置 false」与 §3.1.2「探针对**该表**通过」相互矛盾

- **位置**：§3.0 末句（L77-78）vs §3.1.2（L89-92）
- **问题**：前者是全局开关语义，后者是逐表门控语义；且逐表结果如何持久化到运行时（配置名单？模块常量？）完全没有交代。
- **建议**：与 B2 一并统一为「显式名单 + 代码默认不下推」（见 B2 建议 1）。

### M-6 §3.1.3 聚合断言失败后的**处理动作**未定义

- **位置**：§3.1.3（L96）、§5.1（L200）
- **问题**：写了「聚合前断言 `sum(各子窗 rows) == concat 后 rows`」，但断言失败是上抛、还是 WARNING + 全列去重后继续？passthrough 全量覆盖语义下，静默写入重复行即为数据污染。
- **建议**：明确——断言失败 ⇒ 先按全列去重重试一次，仍不等 ⇒ **上抛并禁止写入**（不得落库）；§5.1 增加「断言失败 → 不写库」用例。

### M-7 `passthrough_export_window_pushdown` 代码默认 true 与「默认不改行为」不一致

- **位置**：§3.4（L155）
- **问题**：代码默认 true 意味着任何未显式配置的 profile（含未来新建）会在**没有探针证据**的情况下开启窗口下推，与 B2/M6 的风险处置方向相反，也弱化了「纯增益、默认不改行为」的立场。
- **建议**：代码默认改为 **false（fail-safe）**，由 profile 在探针通过后显式置 true；并在 §5.4 明确「未见探针证据 → 窗口下推保持关闭」。

-  positives：M1 的异常契约修订**准确且可直接据以编码**（所引 `client.py:570/596/564-566` 逐条对得上）；M2/M3/M4/M7/M9 与 S1–S4、S6–S10 闭环质量良好；章节编号与术语一致性无问题；代码锚点全部有效。
