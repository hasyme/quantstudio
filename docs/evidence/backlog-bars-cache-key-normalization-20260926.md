# backlog · bars 缓存键规范化 + 单形态预取（2026-09-26 登记）

- 来源：全池共享 bars 缓存项目（`docs/backtest-pool-shared-bars-cache-design.md`）的 **V5 计量暴露**
- 状态：**待立项**（未排期；本项不绑定已落地笔，须单独立项）
- 类型：**纯性能型**（可观察结果不变，须以四重等价性为验收）

---

## 一、现象（V5 实测）

全池共享落地后（断板反包 2 交易日，同机同库影子库）：

| 指标 | 值 |
|---|---|
| wall | 23.5 s / 2 日 ⇒ **11.7 s/日** |
| 池批量预取 | **3 批 / 累计 8.83 s** ⇒ **约 4.4 s/日**（占 wall **38%**） |
| 单码 SQL | 1.0 次/日（基线 1,001/日，已达标） |

**根因**：为免疫 code 形态差异（池用 `_to_ptrade_code` 带后缀形、策略以 `_bare` 剥后缀后的裸码请求），
池采用**双形态入池**（2000 entries = 1000 codes × 2 形态）⇒ 单次全池批量预取的代价约翻倍
（P3 实测单形态 1000 codes × W60 = 0.99s；双形态 2000 entries ⇒ 约 2-3s/批）。

## 二、建议方案（待立项细化）

**缓存键规范化 + 单形态预取**：
- 将 bars 窗口缓存的键**规范化**（如统一为裸码形，或统一为带后缀形），使同一标的的不同书写形态映射到**同一缓存条目**；
- 池预取仅取**规范形态**一份 ⇒ 预取数据量减半；
- 预期：预取成本 **4.4 → ~2.2 s/日**，wall **11.7 → ~9.5 s/日（−19%）**。

## 三、为何单独立项（不绑已落地笔）

1. 键规范化涉及**缓存键语义**改动，影响**全策略族的形态匹配**（含 ETF/指数/股票多形态书写），
   属新的一次纯性能型改动；
2. 须重走「**预证前置** + 四重等价性（切片逐位 / nav_sha / 6 策略横验 / pytest）」；
3. 与已落地笔绑定会拖长闭环、放大回归面，收益（−19%）不足以承担该风险。

## 四、立项时必须覆盖的前置预证（沿用本案纪律）

- **P1'** 规范化后键匹配：同一标的不同形态请求必须命中同一条目（正例 + 反例双向验证）；
- **P2'** 规范化切片 vs 直连 SQL 逐位一致（400 codes × 多 count，判据 0 不一致）；
- **P3'** 预取数据量与耗时前后对照（目标：数据量 −50%、批量耗时 −50%）；
- **P0'**（新增检测型同款）**功能生效验证**：命中率不下降（应仍 ≈99.9%）、单码 SQL 不回升。

## 五、风险

| # | 风险 | 缓解 |
|---|---|---|
| R1' | 规范化映射错误 ⇒ 命中率下降或错码取数 | P1' 双向验证 + P2' 逐位比对；未过即回退 |
| R2' | 部分策略族使用非标准代码形态 ⇒ 规范化后失配 | 保留「原形兜底命中」路径（先查规范键，未命中再查原形键） |
| R3' | 与本案池状态管理交织（seeded/扩窗） | 规范化只作用于**键**，不动池状态机；池状态语义逐字保持 |

**登记纪律**：本项不得以"已登记"关单（参见铁律「框架问题立即解决：禁止登记挂账替代修复」）——
本项为**已识别优化空间**（非框架缺陷），登记属正常 backlog；一旦决定推进，须当轮启动并走六步流水线。

## 六、预证结案（2026-10-01，总调度审计采信）

**状态：CLOSED — 归因推翻，真瓶颈另修（另件已闭环）**

本轮立项前的四项预证（P1'/P2'/P3'/P0'）实测**推翻本件两项主张**：

| 本件主张 | 预证实测 | 判定 |
|---|---|---|
| 双形态入池（2000 entries）⇒ 预取代价约翻倍 | 双形态池 5.247s vs 单形态 1000 有效码 6.478s（同为内存路径）⇒ **带后缀无效码近零成本** | **不成立** |
| 池需双形态以免疫 code 形态差异 | 池 / 请求 / 缓存键**均为库内裸码**；数据访问层收到的请求码**恒为裸码**（`ptrade_api` 以 `bare_codes` 调用，L1441/L1450 实证）；绕过 ptrade_api 直连时带后缀形返回**空** | **前提误判**，双形态入池并未实现形态免疫 |

**真瓶颈（预证另测）**：池预取走 PR7 全历史加载（`SELECT … WHERE code IN (…)` 无 time/count 过滤）
——「拉全历史只为取 30 根」，Python 后处理占全路径 **86%**（等效 SQL 直取 0.821s vs impl 5.800s）。

**处置（总调度裁定）**：
- 「单形态预取」——**不做**（收益≈0，且会削弱既有形态免疫兜底）；
- 「键规范化」——**不随该件**（真实链无影响面、无收益；若将来出现带后缀请求路径，
  另立**功能修正件**——那属行为变化：空 → 有数据）；
- 真瓶颈修复——**另件**（bars 池预取窗口 SQL 化，纯性能型，实测 6.145→1.118 s/1000 码，−81.8%）：
  见 `docs/backtest-bars-pool-prefetch-window-sql-design.md` +
  `docs/evidence/bars-pool-prefetch-window-sql-20261001.md`。

**本件结论**：backlog 条目所载「4.4 → 2.2 s/日」路径不成立；同域真收益由另件以更大口径达成。
