# 缺陷1 取证定稿：污染源确证（2026-09-28 深夜，③ 取证完成）

> **本文以直接证据回答「污染物从哪来」，纠正此前两处误判。
> 结论：污染不是 QFQ/口径问题，而是「停牌占位 bar 被写入未复权价」。**

---

## 0. 先纠正我此前的两处错误结论

| # | 我之前说 | 实际 | 怎么发现的 |
|---|---|---|---|
| 1 | "两次重跑零写入" | **错**。upsert 原地覆盖 + DuckDB autocommit，写入已提交 | 行数不变≠没写；`writers.py:836` `ON CONFLICT DO UPDATE` |
| 2 | "污染公式 = raw × adj_factor（乘了因子本身）" | **不准确**。是 `cloud × adj_latest/adj_i`（即 `_restore_to_raw` 公式被误施加于 stock_minutes） | 见 §3 定量比对 |

## 1. 污染物（000963 @ 2026-01-08）全字段

```
本地 stock_minutes:  code=000963  time=14:58 / 14:59
                     open=high=low=close=538.03
                     volume=0.0   amount=0.0   suspendFlag=1
                     close_front=NULL
本地 stock_daily:    close=39.05（真值 raw）
```

**该 code 全天只有 2 根 bar（14:58、14:59），均为 `volume=0, suspendFlag=1`。**

---

## 2. 云端真值（直取 MCP，同日）

```
000963.SZ 2026-01-08 14:59:00  close=39.07  vol=0     adj_factor=1.0
000963.SZ 2026-01-08 15:00:00  close=39.05  vol=59508 adj_factor=1.0
```

**云端返回完全正确**：14:59 = 39.07、15:00 = 39.05（与 daily raw 39.05 一致），
且云端 `adj_factor` 恒为 **1.0**。

→ 云端无污染、口径正确；**污染发生在写入链路**。

---

## 3. 定量定位污染公式

```
local / cloud = 538.03 / 39.07 = 13.7709
云端 adj_factor            = 1.0
aux 表 adj_i(@2026-01-08)  = 13.4846
aux 表 adj_latest          = 13.9577
adj_latest / 云端adj_factor = 13.9577 / 1.0 = 13.9577
```

**实测比值 13.7709 与 13.9577 相差 1.34%** → 与 `_restore_to_raw` 的公式
`raw = qfq × adj_latest/adj_i` **一致**。

即：**`stock_minutes` 被施加了「云端 qfq → raw」的还原乘法**，
而 A′ 明确认定该表口径为 raw、**不应还原**。

### 3.1 与 A′ 代码的关系（重要）

`mcp_adapter._restore_to_raw` 中：

```python
if str(table) in _QFQ_CALIBER_TABLES:   # {stock_daily, etf_daily, etf_minutes}
    ratio = (adj_latest / adj_i).where(valid, 1.0)
else:
    ratio = pd.Series(1.0, index=out.index)   # stock_minutes → 1.0，不还原
```

A′ 实施后 `stock_minutes` 走 `ratio = 1.0`，**不会**产生 13.77× 放大。

→ **这些污染行是 A′ 之前（旧公式）写入的历史遗留**，不是本次 A′ 造成的。
佐证：`update_time` 显示为 **2026-09-24 及更早**（A′ 于 09-28 实施）。

## 4. 污染的分布特征（全表实测）

| bar 时刻 | 行数 | volume=0 | suspendFlag=1 |
|---|---|---|---|
| **14:59** | 782,602 | **782,602 (100%)** | **782,602 (100%)** |
| **15:00** | 781,818 | 2,359 (0.3%) | 2,359 (0.3%) |

- `(code, day)` 中有 781,818 组**同时**存在 14:59 与 15:00 两根 bar，
  其中两者 close **仅 36.8% 相等**；
- 有 **784 组只有 14:59**、无 15:00（如 000963 @01-08）。

**`14:59` bar 全部为 `volume=0 + suspendFlag=1` 的占位 bar**，
其 `close` 在多数情况下与真实 `15:00` 收盘 bar 不同。

### 4.1 但注意：14:59 并非"系统性错误"

以日线 raw 为准比对：14:59 一致率 **80.27%**、15:00 一致率 **82.77%** —— 两者接近。
故**不能简单断言"14:59 全错、15:00 全对"**；污染是与**特定 code/日期**相关，
而非与 bar 时刻强相关（000963 是极端个例：ratio 13.77）。

## 5. 已确证结论

1. **云端口径正确**（`stock_minutes` = raw），A′ 口径矩阵成立、`_QFQ_CALIBER_TABLES` 判定正确。
2. **污染是历史遗留**（`update_time` ≤ 2026-09-24 15:06，早于 A′ 09-28 实施），
   由**旧版还原公式**在 `stock_minutes` 上误施加 `adj_latest/adj_i` 造成
   （实测比值 13.7709 ≈ `adj_latest/云端adj_factor` = 13.9577，差 1.34%）。
3. **A′ 已从根上消除该路径**（该表 ratio 恒为 1.0，不再还原）。
4. **两次修复重跑一行未写**（`update_time` 停在 09-24 15:06）——
   分别在 fetch 阶段 batch ~131（预算错误）与 batch 28（看门狗超时）中断。
   **机理修正（2026-09-29，依审计 F2）**：**不是写事务回滚**——
   writer 逐片 `write()` 独立连接、无显式事务、upsert 后关连接 → **逐片 autocommit 即持久**
   （`writers.py:788-860`）；「全部片写完后一次」的**只有水位**（`daemon.py:1343-1350`）。
   真正原因 = **fetch 是「全量前置阻塞」**（`mcp_adapter.py:1596-1626`：先循环取完全部 136 批、
   落盘 parquet，才 return 分片迭代器）→ fetch 未完成 → **一片都未 yield → 无任何写发生**。
   **数据无任何变化，亦无损坏。**
5. **待决**：重跑策略需解决"单次全量跑不完"（136 批 ≈ 10h fetch），
   且 fetch 相位在 daemon 侧无可停边界（游标只在写片后推进）。见 §8。

## 6. 仍未解的一点（不得跳过）—— **已解，见 §6.1**

第一次 full_range 重拉覆盖 2026-01-05~02-12（batch 1–22）后，
该段污染率**未下降**（4.09% vs 未覆盖段 3.72%）。

三种可能：
- (a) 该段实际未写入（事务/游标原因）；
- (b) 写入了，但另有第二条写入路径仍在放大；
- (c) 覆盖写入的值本身仍错。

### 6.1 结论：(a) 成立 —— 两次重跑确实一行未写

**决定性证据 = `update_time`：**

```
stock_minutes 最新 update_time = 2026-09-24 15:06:27
stock_daily   最新 update_time = 2026-09-24 12:04:17
```

A′ 于 **2026-09-28** 实施；两次修复重跑亦在 **09-28**。
**全表最新写入时刻停在 09-24 15:06** → **两次重跑未写入任何一行**。

→ 我最初的判断「零写入」**是对的**；中途据"分段污染率 4.09% vs 3.72%"改成
"写入已提交但未修复"**是错的**（该差异纯属数据自然波动，非修复信号）。

**为什么没写**（机理修正，依审计 F2）：**fetch 是「全量前置阻塞」**——
`_resolve_shard_paths`（`mcp_adapter.py:1596-1626`）先循环 `for i, (bs,be) in enumerate(batches)`
取完全部 136 批并落盘 parquet，**才** `return paths, job_id`；daemon 的逐片
align→validate→write 在此之后才开始。
两次重跑分别在 fetch 的 batch ~131（预算错误）与 batch 28（看门狗超时）中断
→ **一片都未 yield → 无任何写发生**。
（**非**写事务回滚：writer 逐片独立连接、upsert 后关连接 = autocommit 逐片即持久，
`writers.py:788-860`；「全部片写完后一次」的只有水位，`daemon.py:1343-1350`。）

**(b) 亦已排除**：`aligner._apply_qfq` 只写 `{col}_front` / `{col}_back` **新列**
（`aligner.py:988/992`），**从不回写 `close`**。
