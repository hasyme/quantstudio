## 1. 纠正：写入已提交，但未修复

前文基于 `stock_minutes` **行数未变**（194,994,044）判定「零写入」——**错误**。
writer 用 `INSERT ... ON CONFLICT DO UPDATE`（upsert，`writers.py:836`）**原地覆盖**，
行数本就不会变。且流式路径**无显式 commit**（DuckDB autocommit），故每片写入即持久化。

**正确判据 = 分段污染率对比**（本次重拉覆盖 batch 1–22 = 2026-01-05 ~ 2026-02-12）：

| 分段 | 配对数 | >5% 污染 | 污染率 |
|---|---|---|---|
| A 已重拉（01-05 ~ 02-12） | 248,523 | 10,169 | **4.09%** |
| B 未重拉（02-13 ~ 09-16） | 1,312,825 | 48,876 | **3.72%** |

**重拉段污染率不降反略升 → 重拉未修复任何数据。**

## 2. 污染公式（已定量锁定）

抽样 `000963 @ 2026-01-08`（A 段，已重拉，仍污染）：

| 量 | 值 |
|---|---|
| 本地 `stock_minutes.close` | **538.03** |
| `stock_daily.close`（raw 真值） | 39.05 |
| 本地/真值 | **13.7780** |
| `adj_factor`@2026-01-08 | 13.4846 |
| `adj_latest` | 13.9577 |
| raw × adj_i | 526.57（差 2.2%） |
| raw × adj_latest | 545.05（差 **1.3%**） |

**结论：污染公式 = `local = raw × adj_factor`**（乘了因子**本身**，量级 ~13.5），
**不是** `raw × adj_latest/adj_i`（那只有 1.035，量级不符）。

即：**复权因子被乘反了方向**——本应 `raw = qfq × adj_latest/adj_i`，
实际写成 `× adj_i`（或等价地把 raw 当成 qfq 又乘一次因子）。

## 4. 回答「能否通过框架整体调整修正」

### 4.1 现象拆解

| 子问题 | 层次 | 框架能否整体修正 |
|---|---|---|
| ① `export_exceeds_time_budget` | 云端配额/传输 | ✅ 已由 `export_async=true` 配置解决 |
| ② 失败后无退避重放循环（空转 5h） | **框架缺陷** | ✅ 可修（框架层，重试策略） |
| ③ 全量重拉不修复污染 | **框架缺陷（核心）** | ⚠️ 需先定性再定方案 |
| ④ 单次全量跑不完（136 批 × 4.4min ≈ 8h） | 框架能力 | ✅ 已有 `TaskResumeCursor` 续传机制可复用 |

### 4.2 关于 ③：为什么重拉没修复

A′ 对 `stock_minutes` 的动作是 **ratio = 1.0（不还原）**，即**原样透传云端值**。
云端值正确（39.05），但本地存 538.03 → 说明**污染不在 A′ 的还原公式**，
而在 **A′ 之后的链路**（aligner 的 front/back 计算、或 validator、或 writer 归一）。

→ 这解释了为何 A′ 修好了"日线表"却修不好"分钟表"：
**分钟的污染源与日线不同**，不在 `_restore_to_raw` 这一层。

### 4.3 框架整体调整的可行路径

1. **先定位 ③ 的确切写入点**（必须取证，不得猜）：
   在 `_stamp_and_write` 前后插桩，比对同一 `(code,time)` 的 aligner 输入/输出与落库值。
2. **③ 属框架层修复**（aligner/writer 归一逻辑），符合「全链路修复仅限框架层」铁律。
3. **④ 用既有 `TaskResumeCursor`**（`daemon.py:738`）——已在流式路径接线
   （`daemon.py:1326` 每片调 `_task_boundary`），只需让 `--mode once` 下发
   `cancel_check` 即可启用续传；**无需新造分段机制**。
4. **② 框架层加重试上限 + 退避 + 明确失败退出**。
