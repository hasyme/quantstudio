## 三、P0 缺陷（必须修订，阻断实施）

### P0-1 · 失效链叙述与文档自有证据矛盾

设计文档 §1.2 宣称「精确闭环」：`front` 由被放大的 `close` 推导 → `front = raw`（错值）。

但取证报告 **§3.1（000012.SZ）** 落库 `close_front = 4.0861 = raw × adj_i/adj_latest`，标注
「该列**正确**」——这**不是** raw（raw 应为 4.110）。且全量形态分布中主导形态是
「front 正确 / raw 失真」占 **45.3%**，与 §1.2 链预测的「front = raw」（实测仅 8 格，0.1%）直接冲突；
只有 600649 这类少数案例符合该链。

**真实情况是存在至少两条写入路径 / 批次形态，文档未归因。**

- 这不动摇方案 A 的正确性（源头判定对一切下游形态都有效）；
- 但 §1.2「精确闭环」「front 同样失真（值=raw）」「front 是被污染的 close 推导出来的」等表述是**错的**；
- 数据修复的归因论证（§4「两列同修」的机理说明）必须改写为：约半数单元格 `front` 本就正确，重拉后
  两列一并复位，而非「front 全错」。

### P0-2 · 方案 A 判定粒度未定义，伪代码的「批次参考 bar」可能错误

P1-③ 注释自身的观测就是**行级异质**（「is_qfq=False 行并非真 raw，而是旧基准前复权」），说明云端状态
可以按行 / 按日期不同。

若按「每 code 每批次单点判定」，跨越除权日的批次内混合状态会被误判。**必须改为 per-(code, day) 判定**
（每日 15:00 收盘 bar 对当日 `stock_daily.close`），伪代码（§3 方案 A）需重写。

**正面论据（应补入方案论证）**：日线未被污染而分钟被污染，说明云端行为按 freq 不同——数据驱动判定天然
兼容此点，这是 A 优于「按 is_qfq 分流」或「按表硬编码」的核心理由。

### P0-3 · `tol` 未定义 + 双候选同时命中无裁决规则

方案 A 伪代码使用 `tol`，但全文未给值。当 `adj_latest/adj_i ≈ 1`（除权幅度 < tol）时
`cand_raw ≈ cand_qfq`，两候选同时命中，判定歧义。

**必须规定**：
- `tol` 具体值（建议：绝对 `0.01` 元 + 相对 `0.1%` 双门槛）；
- 双命中时的裁决（建议：判 raw、不还原——`ratio≈1` 时还原与不还原数学近似等价，选无副作用路径）；
- 两候选均不命中时 fail-fast 的告警通道与目标。

### P0-4 · 云端与日线 raw 存在 6.5% 不一致（7/107）未归因

取证 H1：云端 close == 日线 raw 仅 `100/107 = 93.5%`，偏离 `7` 行未归因。这是方案 A fail-fast 分支的
**实测触发率下限**。若这 7 行是口径差异（如日线来自 tushare 的舍入差）而非真 qfq，正常批次会被误阻断——
直接命中回退条件 5（fail-fast 触发率异常升高，导致正常批次被阻断）。

**实施前必须归因这 7 行，并据此定 `tol`。**

## 二、三个声明风险点核实

**① 性能未优化 —— 属实，且比声明更重，建议 R3 升级为验收门禁。**
`_get_local_daily_close` 每分片调用一次，SQL 无时间窗口（全历史 close），
`fetchall` 构造 Python 嵌套 dict（千万行级 → 内存峰值 GB 级、耗时秒~十秒级/分片）。
建议验收时先跑基线：单分片读库 >30s 或内存 >1GB，则时间剪枝
（只查分片日期 ±1 天，与 audit 侧 `w_lo/w_hi ±86_400_000` 同构）必须先行，
不得作为纯优化后置。

**② 日线表自引用 —— 核实无死锁；实际风险形态是「读失败降级」。**
同进程 writer 持锁时 read_only connect 可能失败 → `except → {}` → 无参考路径。
日线增量新日期 ratio≈1 恒成立（adj_i==adj_latest）→ 直写不受影响；
ratio≠1（历史重灌）才触发 fail-fast。最坏行为=阻断+告警，不写坏数据。安全。

**③ 参考查询无时间剪枝 —— 属实。** 与①同项，R3 验收处理（剪枝同时解决耗时与内存）。

## 三、验收前确认项

- **C1（trade_date 整型风险，关联缺陷2）**：`_bar_day_of` trade_date 分支用
  `pd.to_datetime(errors="coerce")`；若生产日线 trade_date 为 YYYYMMDD **整型**，
  会被按 ns epoch 解析成 1970-01-01 → 历史重灌（ratio≠1）整批 fail-fast。
  增量场景（新日期 ratio≈1）不受影响；但**缺陷2 数据修复必然重灌历史日线，届时必踩**。
  要求：验收时用真实分片确认 dtype；若为整型，`_bar_day_of` 补
  `astype(str)` + `format="%Y%m%d"` 分支。单测当前仅覆盖 "2026-06-15" 字符串。
- **C3（验收监控信号）**：`classify_no_ref_passthrough` 混合「真新日期直写」与
  「day 解析失败但 ratio≈1 直写」两类。验收 checklist 增加：该计数对比新增交易日数，
  异常升高 = `_bar_day_of` 解析或参考读取异常（含 read_only 连接失败）。

## 四、P2 建议（不阻断）

- **P2-A**：audit 补漏检日线查询 `except → continue` 无日志（与既有 A1 codes 查询
  风格一致），补漏检静默失效不可见，建议加 `logger.warning`。
- **P2-B**：`_bar_day_of` 的 epoch ms 分支（分钟表入库后实际列形态）无单测，建议补。
- **P2-C**：`_get_local_daily_close` 读库失败与「真无参考」共用同一返回路径，
  fail-fast 报错文案（「本地无该日 close」）在基础设施故障时会误导排查，建议区分。
